## 리스크 1: wiki/meetings/actions.md 단일 파일 병목

### 문제점
3~6개월 진행 시 완료된 액션이 수백 개로 쌓임
- 토큰 과다 소비 (LJM이 /ingest마다 전체 파일 읽음)
- 업데이트 오류 (텍스트 통째로 다시 쓰다 내용 누락)
- 가독성 저하

### 보완책: 분기별 아카이브 분리 (추천)

**타이밍**: 매 분기말 또는 월말 자동화

```
wiki/meetings/
├─ actions.md           # 현재 열린 액션만 (~30개)
├─ actions-closed.md    # 최근 완료 (선택사항)
└─ archive/
   ├─ 2026-Q1-closed.md
   ├─ 2026-Q2-closed.md
   └─ ...
```

**구현**:
1. /ingest 커맨드 내장 규칙
   - 완료 액션 발견 → archive/ 분기별 파일로 이동
2. /lint에 경고 추가
   - "actions.md 크기 경고 (200줄 이상)"

## 리스크 2: /ingest 단계에서 LJM의 ID 충돌

### 문제점
LJM이 이전 D-0001, A-0041 기억 못함
- 새로운 결정에 다시 "D-0001" 부여
- 새로운 액션에 다시 "A-0010" 부여
- wiki 전체 ID 중복으로 오염

### 보완책: index.md "현재 상태" + State 확인 단계 (필수)

**ingest.md에 명시**:

```markdown
### 1️⃣ State 확인 (필수!)

wiki/meetings/index.md를 먼저 읽으세요:

## 🔢 현재 상태 (LJM이 읽어야 함)

- **마지막 할당된 D 번호**: D-0015
- **마지막 할당된 A 번호**: A-0087
- **마지막 용어 건수**: 12개

이 숫자들은 매 /ingest 후 자동 갱신됩니다.
```

**결과**: 신규 결정은 D-0016부터, 신규 액션은 A-0088부터 시작 → 100% 충돌 방지

## 리스크 3: "모든 문장 [[출처]]" 규칙의 경직성

### 문제점
"모든 문장"이 출처를 가져야 한다는 규칙
- LJM 파싱 오류 유발
- 가독성 심각하게 떨어짐 (`[[2026-03-05]] [[2026-03-05]]` 반복)
- /lint false positive 과다

### 보완책: "Bullet point 단위" 출처 규칙으로 재정의

**출처 필수**:
- ✅ D의 모든 진술 (결정 내용, 검토 대안, 근거)
- ✅ A의 모든 설명
- ✅ 용어 정의

**출처 불필요**:
- ❌ 헤더 (## 결정 내용)
- ❌ 메타데이터 (**상태**: 확정)
- ❌ 테이블 헤더
- ❌ 순수 데이터 (날짜, 숫자)

**개선된 예시**:
```markdown
# D-0001: 인증 방식 변경

**상태**: 확정       ← 출처 불필요
**출처**: [[2026-03-05]]

## 결정 내용
세션 기반으로 변경한다. [[2026-03-05]]  ← 필수

## 검토한 대안
1. JWT + 블랙리스트
   - 비용: Redis 필요 [[2026-03-05]]   ← 필수
   - 결론: 거절
```

**업데이트**: /lint 규칙 구체화 (false positive 제거)

## 리스크 4: 용어 정규화 미흡

### 문제점
여러 사람이 회의 기록하므로
- "스팩" vs "스펙" vs "Specification"
- "JWT" vs "제이더블유티"
- "마이그레이션" vs "마이그레이션" (띄어쓰기 다름)
- glossary에 동의어가 무분별하게 쌓임

### 보완책: glossary 정규화 프로토콜

**/ingest 단계에 포함**:

```markdown
### 신규 용어 정규화 검사

기존 glossary.md와 비교:
- "스팩" 발견 → 기존 "스펙"과 병합 (신규 추가 안 함)
- "Redis" 발견 → 이미 등재됨 (신규 추가 안 함)
- "PoC" 발견 → 없음 (신규 추가)

사용자 확인:
"정규화 결과:
- 스팩 → 기존 '스펙' 항목에 병합
- Redis → 기존 항목
- PoC → 신규 추가

이대로 할까요?"
```

**glossary.md 구조** (동의어 컬럼 추가):

```markdown
| 정규형 | 동의어 | 의미 | 처음 등장 |
|---|---|---|---|
| 스펙 | 스팩, specification | 상세 요구사항 | [[2026-02-20]] |
| JWT | 제이더블유티 | JSON Web Token | [[2026-03-05]] |
```

**/lint에 용어 검사 추가**:
```
⚠️ "스팩"이 3번 등장했는데, glossary에서는 "스펙"의 동의어입니다.
   → 본문을 "스펙"으로 정규화할까요?
```

## 부수적 개선: 예시 데이터 싱크

### 문제
설계 문서의 예시가 불일치
- D-0001에서는 A-0042가 "Bob의 PoC"
- actions.md에서는 A-0041이 "Bob의 PoC", A-0042가 "Carol의 FE"

### 해결
모든 프롬프트 + 문서에서 일관된 예시 사용

**정정된 예시**:
```
D-0001: 인증 방식 변경
├─ A-0041: Bob의 PoC 구현
├─ A-0042: Carol의 FE 연동
└─ A-0043: 저장소 분석 (미결에서 파생)
```

프롬프트 프레임워크(ingest.md 등)에 이 테이블을 포함하면 LJM이 예시를 보고 헷갈리는 일 없음
