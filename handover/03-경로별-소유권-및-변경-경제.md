# 03. 경로별 소유권 및 변경 경제

**작성일**: 2026-09-17  
**목적**: LJM vs 사람의 명확한 역할 분담과 신뢰도 유지 원칙

---

## 핵심: 신뢰할 수 있는 SSOT의 조건

SSOT가 신뢰받으려면 **LJM이 규칙을 우회할 수 없어야 합니다.**

시간이 지날수록:
- ✅ LJM이 규칙을 100% 따르면 → SSOT 신뢰도 ↑
- ❌ LJM이 규칙을 임의로 무시하면 → SSOT 신뢰도 ↓↓↓

---

## 경로별 소유권 매트릭스

| 경로 | LJM | 사람 | 이유 |
|---|---|---|---|
| **wiki/meetings/** (원본 회의록) | 읽기만 | 원본 작성 | SSOT는 불변 |
| **wiki/meetings/*.md** (메타) | 생성/갱신 | 검토 | LJM 소유, 사람이 품질 보증 |
| **CLAUDE.md** | 제안 | 승인/수정 | 행동 규칙을 LJM이 스스로 완화하면 신뢰 하락 |
| **SCHEMA.md** | 제안 | 승인/수정 | 스키마가 흔들리면 모든 검사도 흔들림 |
| **.claude/commands/** | 실행 | 변경 승인 | 검사 규칙을 LJM이 몰래 수정할 수 없게 |

---

## 계층별 설명

### 1️⃣ wiki/meetings/ (원본) — 읽기만

**LJM의 역할**:
- 읽기만 가능
- 원문 분석 후 보고
- 오류 플래그 (수정은 사람)

**사람의 역할**:
- 원본 회의록 작성 (Notion .md 내보내기)
- 기록 오류 발견 시 수정 (주의: 과거 회의록은 건드리지 않기)

**이유**: 원본이 바뀌면 SSOT의 기준이 무너집니다.

---

### 2️⃣ wiki/meetings/*.md (메타) — LJM 소유, 사람 검토

**LJM의 역할**:
- decisions.md, actions.md 빠르게 생성/갱신
- 규칙(SCHEMA.md)에 정확히 따라서만 동작
- 피드백 반영해서 수정

**사람의 역할**:
- ingest 결과 검토
- 파싱 오류/분류 오류 인라인 수정
- 최종 승인 후 commit

**이유**: LJM이 빠르게 만들고, 사람이 품질을 보증합니다.

**협업 흐름**:
```
1️⃣ LJM: decisions.md 생성
   ↓
2️⃣ 사람: 읽어보고 피드백
   "이 결정이 왜 D-0001이고 D-0002가 아닌가요?"
   ↓
3️⃣ LJM: 수정
   "확인했습니다. 이렇게 조정했습니다."
   ↓
4️⃣ 사람: 최종 OK
   "좋습니다. 승인합니다."
```

---

### 3️⃣ CLAUDE.md — 제안은 LJM, 결정은 사람

**LJM의 역할**:
- "이 규칙이 부족해 보입니다" (제안)
- "이 경우를 어떻게 처리할까요?" (질문)

**사람의 역할**:
- 규칙을 명시적으로 수정
- "이 항목을 추가하겠습니다"
- LJM에 알림: "새 규칙이 바뀌었습니다"

**예시**:

❌ **LJM이 독단** (금지):
```
"이 규칙이 너무 복잡해서 이번에는 제외하겠습니다."
```

✅ **LJM이 제안** (OK):
```
"현재 /lint에서 '모든 Bullet에 출처 필요'라는 규칙이 있습니다.
하지만 이렇게 하면 false positive가 많이 발생합니다.
제안: 테이블이나 메타데이터는 제외하는 것이 좋을 것 같습니다."
```

✅ **사람이 결정** (OK):
```
"좋은 제안입니다. SCHEMA.md와 lint.md를 이렇게 수정하겠습니다: [상세]"
```

**결과**: LJM이 규칙을 우회하지 않습니다.

---

### 4️⃣ SCHEMA.md — 명확한 정의, 해석 금지

**LJM의 역할**:
- SCHEMA.md에 정의된 대로만 동작
- 해석하지 않기
- 명확하지 않으면 사람에게 물어보기

**사람의 역할**:
- 명확한 규칙 정의
- 애매한 경우 추가 명시

**예시**:

❌ **LJM이 해석** (금지):
```
"상태가 '논의중'이면 기한을 없어도 되겠네요."
```

✅ **LJM이 정의 확인** (OK):
```
"SCHEMA.md를 보니 상태와 기한이 모두 필수입니다. OK 진행하겠습니다."
```

❌ **LJM이 임의로 수정** (금지):
```
"이 결정이 너무 크니까 여러 개로 쪼갤게요."
```

✅ **LJM이 사람에게 물어보기** (OK):
```
"이 결정이 너무 크면 어떻게 할까요? 보고 후 결정이 필요해 보입니다."
```

---

### 5️⃣ .claude/commands/* — 검사 규칙은 사람 소유

**LJM의 역할**:
- ingest.md, lint.md 정의된 대로만 실행
- 검사를 건너뛰지 않기
- "이 항목은 검사 대상이 아닐 것 같아요" 임의 판단 금지

**사람의 역할**:
- 검사 규칙 정의 (ingest.md, lint.md 수정)
- LJM이 고칠 수 없게 보호

**변경 방식**:
```
ingest.md 수정할 때:

## 3단계: State 확인

이전:
LJM이 하는 대로

현재:
LJM은 반드시 index.md의 "현재 상태"를 먼저 읽습니다.
- D-XXXX 마지막 번호
- A-XXXX 마지막 번호

[2026-03-20] 수정: State 확인을 반드시 첫 번째 단계로 변경
```

LJM에 알림: "ingest.md가 업데이트되었습니다."

---

## 변경 경제 (Change Economy)

### 위험한 구조 🔴

```
LJM이 할 수 있는 것:
- wiki 수정
- 규칙 해석
- 검사 기준 조정
- "효율성 때문에" 규칙 우회

결과:
→ 시간이 지날수록 신뢰도 하락
→ "이게 정말 SSOT인가?" 의문
→ 창고가 됨
```

### 신뢰 가능한 구조 🟢

```
LJM이 할 수 있는 것:
- wiki 생성/갱신 (SCHEMA 틀 안에서)
- 규칙 실행
- 위반 명확히 보고
- 개선 제안 (사람이 승인 필수)

결과:
→ LJM = 신뢰할 수 있는 도구
→ "이것이 SSOT다" 확신
→ 살아있는 시스템
```

---

## 신뢰도 = 일관성

```
시간 경과에 따른 신뢰도 변화

100% ┤     ✅ 규칙 완전 준수
     │     /
     │    /
     │   /
 50% ├──/────── ❌ 규칙 해석 + 우회
     │ /
     │/
  0% └───────────────────
     0m  1m  3m  6m
```

**LJM이 규칙을 100% 따르면 신뢰도는 계속 상승합니다.**

---

## 최종 원칙 5가지

1. **모든 규칙 변경은 사람이만**합니다
   - LJM은 제안하고 사람이 최종 결정

2. **규칙 해석은 허용하지 않습니다**
   - 명확한 규칙이 우선
   - 그레이 존은 인라인 토론

3. **LJM은 규칙을 우회할 수 없습니다**
   - "효율성 때문에" "특수한 경우" "이번만" 금지

4. **모든 변경은 추적됩니다**
   - Git / audit log로 누가 언제 뭘 바꿨는지 기록

5. **신뢰는 일관성에서 옵니다**
   - LJM이 규칙을 100% 따르면 SSOT가 성립
